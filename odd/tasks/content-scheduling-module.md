# Content scheduling module

## Objective and problem
Add a "Cronograma de contenidos" module to the CRM so the marketing team can plan, track and share social media content for an arbitrary number of content projects. The source specification (`Especificacion modulo contenidos Maia.docx`) describes three initial grids (Maia Consultores, Maia Plagas, Maia Residuos), a monthly important-dates calendar, and a set of customization requirements. None of this exists today: the repository has no content/marketing domain. The existing Campañas module models outreach execution, not editorial grids, and is not reused.

## Confirmed product decisions
- One reusable module with dynamic content projects. The three Maia brands are seeded initial data, never hardcoded tabs, tables or enums. New projects are created from the UI.
- Each project configures its own pillars, topics, goals, formats and channels, and its own typed custom fields and sections (text, long text, date, number, single/multiple selection). Creating a project or a custom field must not require code changes or physical columns.
- Access is restricted to the users assigned to the project. Enforcement is server-side for listings, detail, direct URLs, downloads and exports.
- Each project has its own important-dates calendar. Only the administrator gets a consolidated cross-project view, filterable to one, several or all projects. Other users only see their assigned project calendars.
- Trash keeps attachments so restoring a content recovers them.
- Duplication copies text, selections, custom values and attachments, clears the planned date, and resets status to "Incompleto". The original is untouched.
- Concurrent edits warn the later editor instead of silently overwriting.
- Publication stays manual. No social network APIs, metrics or automatic publishing.
- Attachments: accepted formats are JPG, PNG and WEBP for images and MP4 and MOV for videos; 10 MB per image and 200 MB per video; at most 10 attachments per content; stored privately with authorized download; and no automatic purge, so a trashed content keeps its files until an administrator empties the trash. The specification also allows attaching external links to images or videos, which do not consume the upload limits.

## Scope and constraints
- Additive and isolated: new tables, models, services, policies, views, permissions and tests. Do not redesign or replace existing modules.
- Shared integration surfaces are limited to routes, sidebar navigation, permission seeding and frontend asset registration. Treat those as regression-sensitive.
- Do not change the global timezone. `config/app.php` hardcodes UTC; `APP_TIMEZONE` has no effect. Publication times are entered and displayed in `America/Lima` and stored as UTC instants.
- Do not change `app/Services/DocumentService.php` semantics. It hard-deletes metadata and files and has no video allowlist, so it cannot back restoreable media. The module needs its own media lifecycle.
- Existing CRM owner/team scopes do not equal content-project membership. Add explicit content-project scope.
- Preserve the unrelated in-progress changes present in the working tree (course talks, users, email, UI, fonts, tests). Never stage or commit them.
- No production operation, migration on a real environment, deployment or push.

## Blocking constraint discovered for the attachment phase
Raising the agreed size limits does not work in production as currently configured, and this is verified, not assumed:
- `docker/nginx/default.conf:10` sets `client_max_body_size 20M`, so any upload larger than 20 MB is rejected by nginx with 413 before reaching PHP.
- The production image is `php:8.3-fpm-alpine` (Dockerfile line 4) and the Dockerfile sets no `upload_max_filesize` or `post_max_size`, so PHP keeps its defaults of 2 MB per file and 8 MB per request. Even a 10 MB image cannot be uploaded today, whatever the application claims.
- Local Laragon PHP allows 2 GB, so this will not reproduce in local testing and must not be mistaken for a working feature.
This is an infrastructure decision, not a module decision: it changes the deployment and requires the operator's explicit authorization plus a service reload. Until it is resolved, the module's own validation can be implemented correctly while real uploads above the current ceiling still fail in production.

Operator decision on this constraint: implement the module now with the agreed limits (10 MB per image, 200 MB per video) and treat the nginx `client_max_body_size` and PHP `upload_max_filesize`/`post_max_size` changes as a mandatory deployment prerequisite recorded under T11, to be authorized separately. Do not perform that infrastructure change silently, and do not claim production uploads work on the strength of local tests.

## MySQL migration defect found when the migrations were actually run
The module could not be migrated on MySQL at all, and nothing in the suite could have caught it. Laravel builds automatic index and unique names by concatenating the table and column names, and six of them exceeded MySQL's 64-character identifier limit:

| Identifier (length) | New name (length) |
| --- | --- |
| `content_field_definitions_content_project_id_is_active_sort_index` (65) | `idx_content_field_definitions_project_active_sort` (49) |
| `content_field_options_content_field_definition_id_is_active_sort_index` (70) | `idx_content_field_options_definition_active_sort` (48) |
| `content_item_objective_content_item_id_content_objective_id_unique` (66) | `uq_content_item_objective_item_objective` (40) |
| `content_field_values_content_item_id_content_field_definition_id_unique` (71) | `uq_content_field_values_item_definition` (39) |
| `content_field_value_option_content_field_value_id_content_field_option_id_unique` (80) | `uq_content_field_value_option_value_option` (42) |
| `content_calendar_annotations_content_project_id_annotated_at_index` (66) | `idx_content_calendar_annotations_project_annotated` (50) |

Fixed in `08f6a12` by giving those identifiers explicit short names and following the `idx_` and `uq_` convention the repository's newer modules already use, which this module had failed to follow. Only names changed: no column, table, relationship, cascade or migration order was touched.

Why it mattered: the repository's tests run on SQLite, which has no identifier length limit, so 229 green module tests coexisted with a module that would have failed its first production migration. The earlier verification had already flagged "nothing was verified on MySQL" as a gap; this is what that gap was hiding, and it is the clearest argument in this feature for actually running a migration rather than trusting a green suite.

Recovery performed on the local development database: `000001` and `000002` had applied, `000003` had failed part-way because MySQL does not make DDL transactional, leaving `content_field_sections` and `content_field_definitions` behind and `content_field_options` missing. Those two partial tables were dropped and the migrations re-run. Final state: all eight applied, zero pending, eighteen `content_*` tables, every renamed index present, and `content_items.revision` present as `int unsigned` defaulting to `1`. A pre-migration dump was taken outside the repository before the first attempt.

Still open from that run: the module's two seeders were not executed, so the development database has the schema but no content projects, catalogs or permissions yet, and the sidebar entry will not appear until `ContentPermissionsSeeder` runs. The `feat/aws-storage` branch is now one commit behind this one and needs a rebase or merge before a pull request; it was left alone deliberately because the working tree holds fourteen uncommitted files from another in-flight feature and a rebase would require stashing them.

## Overdue boundary decision
A planned content that carries an explicit time is overdue from that Peruvian instant onwards. A planned content that carries a date but no time is overdue only after that Peruvian day ends, so a content planned for today without a time is not flagged at 00:01. Both cases exclude contents already marked as published. This replaces the looser "compare the stored UTC instant" wording used earlier.

Catalogs, custom fields and sections, members and project archive/settings stay admin-only through the existing `content_projects.*` permissions. Membership never grants anything on a project the user is not assigned to. This supersedes the earlier "Vaciar papelera requires `archive`" rule.
- S2 Archived project = read-only: viewing and exporting stay allowed; every write (contents, ideas, attachments, annotations, trash/restore/purge, catalogs, fields) is refused until the project is reactivated. The consolidated calendar keeps excluding archived projects. This sharpens the T3 statement "archive keeps the project readable".
- S3 Duplicate keeps the " (copia)" title suffix the code already applied; the specification and the user guide were adjusted to say so, instead of removing the suffix. Duplication additionally succeeds when a required custom field was added after the original was created (S14).
- S4 Attachments are added from the content detail page after saving, as implemented; the user guide was adjusted, and after creating a content the user lands on its detail with the attachments section visible.

Rule changes recorded with them:
- The "Overdue boundary decision" above is superseded by S20: the date-only grace was unreachable (every content carries a time), so it was dropped. A non-published content is overdue from its planned Peru instant, including an explicit 00:00. The label is unified as "Atrasado" (S19).
- Exports (S11, S13, S15, S26): headings are formula-neutralised like cells; Fecha `d/m/Y` and Horario `H:i` on the Peru clock plus an "Atrasado" column from the model's own overdue method; inactive custom fields that still hold data are exported with a " (inactivo)" suffix; PDF is capped at 500 rows and Excel at 5000 (`config/content.php`), and an oversized export is refused with a message asking to filter by month, never silently truncated.
- S21 (timezone part) dropped: pinning the MySQL session to `+00:00` was verified locally to shift every existing `TIMESTAMP` by 5 hours (server time_zone=SYSTEM, Peru), so the connection keeps the server time zone. Changing it needs a data migration and a maintenance window; out of scope.
